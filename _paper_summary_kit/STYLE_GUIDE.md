# Structured Summary Style Guide

このガイドは、与えられた情報を QAmatomer 用 JSON に構造化するときの統一ルールです。

ここでいう「与えられた情報」には、たとえば次が含まれます。

- 論文
- 教科書や記事
- 自分で書いたメモ
- 会話ログ
- GPT などの生成 AI に調べさせた結果
- 複数資料をもとにした調査メモ

つまり、これは特定ジャンル専用のガイドではなく、**情報をツリー状に整理するとき全般の指示書**です。

## 目的

- どんな題材でも見た目の骨格をある程度揃える
- 「あとで別の題材でも同じ指示で作れる」状態にする
- 全体像と中身を 2 段階で見やすくする
- 数式や専門記号がある場合でも、JSON 単体で読める形にする
- 題材ごとに無理のない粒度で整理できるようにする

## 出力先

- repo-aware な AI に作らせる場合、使い手はまず `_summaries/` の中に要約用の作業フォルダを 1 つ作る
- 入力ファイルがある場合は、その作業フォルダに入れる
- 入力ファイルがない場合でも、その作業フォルダを作業単位として使う
- AI は、その作業フォルダ内の全ファイルを source として読む
- 出力は同じ作業フォルダ内の `.json` にする
- できれば JSON ファイル名は作業フォルダ名と同じにする
- それが難しい場合でも、テーマが分かる自然な `.json` 名にする
- AI は、その作業フォルダ内のファイルに加えて、自身が持つ知識や追加で得た情報も使ってまとめを作る。ただし、source 由来の情報と混同しない
- 例:
  - `_summaries/bonn_mpim/source_notes.md`
  - `_summaries/bonn_mpim/bonn_mpim.json`

## 想定する入力の型

入力は 1 種類に限らない。

- 1 本のテキストをまとめる
- 複数資料を読み比べてまとめる
- 既存メモを整理し直す
- 生成 AI に調べさせた結果を整理する

どの場合でも、出力では「何を source としているか」が読んで分かるようにする。

## JSON の基本形式

- `annotator-qa-export`
- `version: 2`
- `projects[0].annotations` は原則 `[]`

## ツリー構造のルール

最重要ルール:

- **2段階構成で統一する**
- つまり `root -> section node -> leaf node`
- **leaf の下にさらに子ノードを作らない**
- **ただし `guide` は root 直下で完結する例外にしてよい**

### 望ましい形

- `root`
  - `background`
    - `leaf A`
    - `leaf B`
  - `core`
    - `leaf C`
    - `leaf D`
  - `guide`

このとき `guide` は子ノードなしで、sections に読み順やキーワードを書く形でもよい。

### 禁止したい形

- `root -> section -> subsection overview -> theorem node`
- `root -> section -> subsection -> subsubsection`
- `root -> topic -> subtopic -> detail`

つまり、

- 大きなまとまりの概観
- その中身

の **2段階だけ** にする。

## root の作り方

`root` には少なくとも次を置く:

- 対象の説明
- 一言まとめ
- 重要ポイントの全体像
- このまとめの構成

題材によっては、次のように読み替えてよい。

- 長い technical text なら:
  - 冒頭要約
  - 核となる主張
  - 全体の構成
- 説明文なら:
  - 何を説明するものか
  - 核となるメカニズム
  - どういう順で読むとよいか
- 議論メモなら:
  - 争点
  - 主な立場
  - どこで意見が分かれるか
- 意思決定メモなら:
  - 判断対象
  - 主要条件
  - 比較軸

## section node の作り方

各 section node には:

- そのまとまり全体の概観を 1 つ置く
- 親子関係は `parentId` で表し、その section node に属する leaf を続けて並べる

### 例

- `background`
  - `前提知識`
  - `基本用語`
  - `見取り図`
- `core`
  - `中心概念`
  - `主要な主張`
  - `根拠`
  - `重要例`
section node は「分類棚」であって、細分化を無限に増やす場所ではない。

### section node の概観の中身

最重要ルール：**概観は「この節では○○について説明する」という目次の言い換えにしない**。

概観が薄いと 2 段階構成にする意味がなくなる。**概観を読んだだけでその節の核心が掴める**密度を目指す。

概観に入れるとよいもの：

- 節の中心的な主張・定理・結論を 1〜2 文で明記
- 節内の概念・手法・立場の**比較表**
- 節内の概念の**関係図**（→ や ↔ など）
- 各 leaf に降りる前に知っておくべき枠組みや前提

避けるべき概観の形：

- 「この節では A, B, C の 3 つを見ていく」（leaf の名前を並べているだけ）
- 「○○は重要な概念である」（中身がない）
- 「以下では○○について詳しく説明する」（先延ばし）

よい概観の目安は、「概観だけ読んだ人が、この節のポイントを人に説明できる」状態である。

section node ごとの子 leaf 数は揃えなくてよい。

- 中身が厚い section なら leaf を 3 から 5 個にしてよい
- 中身が薄い section なら leaf は 1 個でもよい
- 無理に左右対称な数にしない

## leaf node の作り方

leaf node は以下のどれかの役割を持たせる:

- 1つの定義群
- 1つの主張群
- 1つの理由群
- 1つの証拠群
- 1つの重要例群
- 1つの比較テーマ
- 1つの手順や判断基準

leaf node の中で、

- exact な主張
- 意味
- 根拠
- 例
- 注意点

を section として並べるのはよい。

ただし leaf の子ノードは作らない。

## 粒度のルール

粒度は **揃えるものではなく、内容に合わせて決める**。

特に次を守る。

- 内容が薄いなら、無理に leaf を分けない
- 1 つの leaf に、自然にまとまる論点をまとめてよい
- 逆に 1 つの leaf が長すぎて読みにくいなら分けてよい
- 「全 section node の子数を揃える」ことは目標にしない
- 「見た目のためだけの分割」はしない

悪い分け方の典型は、1 paragraph 程度の内容を機械的に独立 leaf にしてしまうことである。

よい leaf は、少なくとも次のどれかを満たす。

- 1つのまとまった論点になっている
- 1つの比較単位になっている
- 1つの作業単位・判断単位になっている
- 1つの重要例として独立して読む価値がある

## 内容の優先順位

必ず入れる:

- その題材で中心になる主張
- 読む人がまず押さえるべき前提
- 主要な理由・根拠・証拠
- 重要例
- 比較や判断に効くポイント

あるとよい:

- なぜそれが重要か
- よくある誤解
- 反対意見や例外
- 実用上の含意
- 読み順ガイド

削ってよい:

- 軽微な脱線
- 主線に効いていない細部
- 例の枝葉末節

## source の扱い

source が 1 本なら、その内容を整理してよい。

source が複数あるなら、

- 共通して言っていること
- 食い違っていること
- 自分の整理や要約として付け足したこと

を混同しない。

source が生成 AI による調査結果を含むなら、少なくとも次を意識する。

- 何が source 由来の情報か
- 何が要約・整理・推測か
- 不確かな点があるなら、そのまま断定しない

## 数式・記法のルール

数式や専門記号がない題材なら、この節は無視してよい。

数式を使うときの最重要ルール:

- **元資料の `\newcommand` をそのまま使わない**
- JSON 単体で KaTeX/標準 LaTeX として読める形に展開する
- インライン数式は必ず `$...$` で囲う
- 別行立ての数式は必ず `\[ ... \]` で囲う
- 裸の数式を書かない
- Unicode 数学記号をそのまま置くより、ASCII ベースの LaTeX を優先する

### やってよい

- `\mathbb R`
- `\operatorname{Hom}`
- `\operatorname{Spec}`
- `\mathrm{Id}`
- `X \times_Y Z`

### 避ける

- 元資料でしか定義されていないマクロ
- 例:
  - `\myterm`
  - `\myoperator`
  - `\myspace`
  - `\myfunctor`
  - `\catC`
  - `\objX`
  - `\specialmap`

### 代わりにすること

- `\myoperator` の代わりに
  - `\operatorname{Hom}`
- `\catC` の代わりに
  - `\mathcal C`
- `\objX` の代わりに
  - `X`
- `\specialmap` の代わりに
  - 何の写像かを文章で書くか、標準的な記号で展開する

## 文体のルール

- 日本語で書く
- 元資料のタイトルは原文維持でもよい
- 一言まとめは平易に
- 重要な主張はなるべく曖昧にしない
- 解説は短くてもよいが、核を省かない
- source の文をそのまま長く貼るより、整理し直して書く

## 見出しのルール

- node の見出しは原則として日本語にする
- 元資料の固有タイトルや専門用語は、必要なら原語を併記してよい
- 公開サンプルでも、見出しのためだけに英語へ寄せない

## guide node のルール

最後に `guide` ノードを置き、少なくとも次の一部を入れる:

- おすすめの読み順
- 依存関係
- キーワード索引
- 論点の見取り図
- 判断するときの見方

`guide` は **子ノードを作らず、その node 自身の sections に書く**。
つまり `guide` だけは、root 直下で完結する例外として扱ってよい。

## 命名ルール

- section ノード名は大きいまとまりベース
  - `background`
  - `core`
  - `evidence`
  - `comparison`
  - `guide`
- leaf ノード名は内容ベース
  - `main-claim`
  - `key-example`
  - `pros-cons`
  - `decision-criteria`

## 作成時のチェックリスト

- ツリーは 2 段階構成か
- leaf の下に children がないか
- root に全体像があるか
- section node に概観があるか
- 重要な主張や根拠が落ちていないか
- source と自分の整理が混ざりすぎていないか
- 数式がある場合、元資料の `\newcommand` を残していないか
- JSON は `jq empty` を通るか
